# RepoLadder

A Claude Code plugin (`/map`) that turns a TS/JS repo into a drill-down architecture diagram, published as a Claude Artifact. The top level is plain-language; each level you open goes one step more technical.

## How it works
1. `repoladder summary REPO --fresh` analyzes the repo deterministically into `.repoladder/facts.json` (files, imports, runtime calls, services, endpoints) and prints a digest; on a large repo the digest is folder-first and `summary REPO --part <leaf id>` prints one part's digest.
2. Claude (following `plugin/skills/map/SKILL.md`) writes `.repoladder/grouping.json`: a tree of named groups whose leaves claim files by glob.
3. `repoladder build REPO` validates the grouping (every file exactly once), rolls the file-level facts up into one board per group (`model.json`), lays each board out with D2 (wasm), and writes a self-contained `diagram.html`.
4. The skill publishes the HTML as an Artifact.

**Core rule:** edges are never invented. Every arrow comes from facts and carries file:line evidence. Claude only groups, names and writes summaries.

## Layout
- `src/analyze/`: facts. `resolve.ts` parses with the TS compiler API (syntax only) and resolves imports. `packages.ts` detects packages and kinds (a folder a one-level workspace glob such as `packages/*` names is a package even without its own package.json). `services.ts` maps SDK imports to external services. `calls.ts` matches string literals to server endpoints (runtime call edges); path literals in data positions (object values under non-request keys, string predicates, comparisons) don't count, and React Router page actions match only form posts. HTTP endpoints carry the `methods` the code states (`GET`, `POST`, …; the name stays the bare path), and `routes.ts` follows router mounts inside a `forEach`/`map`/`for…of` over a same-file array literal. `stores.ts` finds database reads and writes per collection/table (Firestore, Prisma, Supabase). `pages.ts` finds pages (client routers, Next.js), `nextjs.ts` Next.js route handlers, server actions and route files, and `remix.ts` React Router / Remix file routes (`app/routes/`, flat, `remix-flat-routes` `+` folders, `react-router-auto-routes` folders, or Remix v1 nested folders, told from the folder shape when there is no `routes.ts`): a module with a default export is a page (its `action` also an http POST endpoint, which only non-GET form posts — `<Form action>`, `formAction`, `submit(…, { action, method })` — match; its loader is not an endpoint), one with only a `loader`/`action` a resource route (http endpoint), a pathless or `_layout` route a layout route file. A hand-listed `app/routes.ts` (`route`/`index`/`layout`/`prefix`) is read from its literal calls, each module classified the same way. `index.ts` ties it together and sorts for determinism. `source.ts` (`FileSource`: the analyzer reads a repo through it, from disk or from an in-memory file set).
- `src/model/`: `schema.ts` (zod schemas for Facts and Grouping), `glob.ts`, `grouping.ts` (default folder grouping and validation; no fixed depth; a folder chain walked in one step is named by its last two folders, skipping `src` and route groups; `splitOversized` splits a leaf holding over 40% (`OVERSIZE_SHARE`) and more than 12 of the files), `depth.ts` (levels must earn their click: no single-child groups, no board of fewer than 3 boxes), `budgetsplit.ts` (no-AI mode: the default grouping splits every board over the digestibility budget, measured on the model, by subfolder, then filename prefix or shared name word, then import clusters named after their most-imported file, and with no seam (or files that would hide in "+N more") into even alphabetical ranges named by their first and last file (`opts.force` splits named leaves even under budget, the oversize pass's way in); `build --default` also splits boards the layout found with too-small names, once, and lays out again), `rollup.ts` (Model: nodes, boards, major edges, hubs, context boxes) with `rollrules.ts` (its pure rules, shared with the page's roll-up), `summary.ts` (the digest Claude reads, with its entry-points section only when the story is on, and `summarizePart`, the per-part digest of two-pass grouping), `tours.ts` (validates guided tours and places each step on the shallowest board that draws it) with `draws.ts` (`drawsEdge`: a major arrow between two boxes, the one test for "drawn" in tours), `compose.ts` (`composeTour`: a file chain to multi-depth tour steps, each hop on its lowest common ancestor's board, at the first dial stop that draws it) with `chains.ts` (`findChains`, a bounded search over `fgraph`) and `tourgraph.ts` (the page data they read, `ChainError`; documented for agents in `docs/tours-data.md`), `derivedtours.ts` (no-AI tours for every build: entry files (pages, endpoints, else a CLI; with no tour from those, a library's entry module and example apps) to a store or service via `findChains` and `composeTour`, 2–4 of the most distinct (one fewer per tour the grouping has), titled by route, endpoint or box name and never twice, mechanical captions; `model.derivedTours` / page `derivedTours`, source "derived"), `flows.ts` (up to 5 flows per board: chains of drawn arrows from an entry to a sink, derived or named in the grouping), `fgraph.ts` (the file-level graph the page carries for the detail dial), `splits.ts` (the grouping's optional `split`s, named by Claude: validated like children, ignored by Default, guarded like any level into the Simple stop's tree) with `simple.ts` (what the page carries for Simple: only what differs from Default and can't be rolled up in the page) and `autosplits.ts` (`build --default` only: the splits for the dial's Less stop, from one more round of `budgetsplit.ts` at `LESS_BOXES`; a grouping Claude wrote is never split mechanically).
- `src/build/`: `layout.ts` (D2 source and layout per board) with `boxsize.ts` (box sizes and the pick among candidates, without D2, so the page shares them), `lane.ts` ("elsewhere" boxes and services in a lane at the board's edge, spaced like the board's own boxes; on by default, `build --no-lane` turns it off), `cylgap.ts` (cylinders stacked in a column are laid out with extra room above and below, so they sit `CYL_GAP` apart; the lint reports `cylGap`), `rangeorder.ts` (a split's even alphabetical ranges that share a column or row trade places into alphabetical order, each taking the old holder's wires where it can, when that adds no wire through a box and at most one crossing, #241), `d2pool.ts` (D2 compiles on a pool of worker instances, started on demand up to the pool size, cached by exact source in `<out>/layout-cache.json`, saved during the build every 500 new compiles or 60 s without pruning, and once more at the end, which prunes; `REPOLADDER_CACHE_SAVE_EVERY` / `REPOLADDER_CACHE_SAVE_MS` override the thresholds), `interrupt.ts` (the CLI's SIGINT/SIGTERM handlers: save the cache, exit 130/143) with `layoutsession.ts` (one pool and a per-board layout memo, keyed by everything a layout reads, for a whole build: the passes of `build --default` share compiles and reuse boards the split left alone, #311; `REPOLADDER_VERIFY_LAYOUT=1` checks every reuse against a fresh layout) and `passes.ts` (that layout/split loop), `timings.ts` (`REPOLADDER_TIMINGS=1` prints `TIMING` phase lines on stderr, each ending `rss=<MB> heap=<MB>`; the `layout#N` line also carries `layoutstats.ts`'s compile counts by direction, spread and lane mode; `REPOLADDER_D2_WORKERS=N` sets the D2 worker count, 1-16; `npm run bench:layout` is the offline layout benchmark, docs/reliability.md), `progress.ts` (`build` prints `[build] ` stage lines and layout board counts on stderr; `--quiet` silences them and, being bare, goes after the root: `build ./repo --quiet`; `buildFromFiles` takes `onProgress` and library callers get nothing otherwise; errors thrown by it are swallowed), `html.ts` (page shell; inlines the packed viewer and page data behind one boot call), `brand.ts` `brandName()` (`REPOLADDER_BRAND_NAME` overrides the shell's product name for recordings; unset, it is `NAME`), `mark.ts` (the owner's mark from `mark.svg` / `mark-dark.svg`, as the page's one data-URI favicon and the header's inline mark; `node scripts/mark.ts` regenerates both), `filepack.ts` (packs the page data: `viewer/wire.ts` reshapes it for compression, then deflate and basE91 via `viewer/base91.ts`; `viewer/unpack.ts` reverses it with the browser's DecompressionStream. The viewer's CSS and JS are packed the same way and unpacked by `viewer/boot.ts`, the page's one inline script, synchronously with `viewer/rawinflate.ts` so the viewer starts as the page parses; `pageViewer`/`pageData` read them back for tooling. `packFonts` packs the Geist and Geist Mono woff2 subsets from `viewer/fonts/` with the OFL text as a third boot argument, which `boot.ts` registers with `FontFace`; `scripts/fonts.ts` regenerates them), `pagesize.ts` (where a page's bytes go, and the page budget), `viewer.ts` (bundles `src/viewer/` with esbuild into minified JS and CSS strings, plus the boot script), `lint.ts` + `outline.ts` (the layout lint, see below). `pipeline.ts` (model, layout passes and HTML from facts and a grouping, shared by `cli.ts` and `lib.ts`; drops the grouping's story unless `features.story`).

- npm package `repoladder` (`npm run npm:pack`, `scripts/npm-package.ts`): the CLI bundle (`bin/repoladder.mjs`, channel `npm`: asks the usage question once in a terminal, `install` runs no npm) plus the library; `.github/workflows/publish.yml` publishes it only from a `v*` tag on `main` in the public repo, through npm trusted publishing (OIDC, no token), approved at the `npm-publish` environment.
- `plugin/`: what ships. `plugin/dist/repoladder.mjs` is the esbuild bundle. `typescript` and `@terrastruct/d2` are pinned in `plugin/package-lock.json`, which Claude Code installs into the plugin's cached copy on install; `repoladder install` (`src/install.ts`) is the fallback. `npm run installcheck` (`scripts/installcheck.ts`, also a CI job on Linux and Windows) installs the plugin with the real `claude plugin install` and builds a fixture with it (after the install it waits up to ~50s for the deps, and dumps `INSTALLCHECK_DIAG` diagnostics before failing); the user-facing install text is `docs/install.md`.
- `test/`: `node --test` with fixtures in `test/fixtures/` (`basic-app`, `multi`, `stores`, `deep` (five levels, with its `grouping.json`), …).

## Conventions
- Node 22 runs the `.ts` sources directly (type stripping): use `.ts` import extensions and erasable syntax only (no enums, no parameter properties).
- Output must be deterministic: the same repo gives byte-identical facts, model and HTML. Sort everything.
- Keep the page self-contained and small: under `VIEWER_KB` (90KB) + `FONT_KB` (60KB) + 1KB per board (`budgetKb` in `src/build/pagesize.ts`; a 121-board repo gets 271KB). The viewer is a fixed ~90KB (its JS and CSS packed, plus the boot script); the Geist and Geist Mono subsets ride in their own blob (`FONT_KB`, outside the viewer ratchet); the packed data grows with the boards, and the Simple stop's new boards (a split's parts and buckets) count as boards. It must follow the Artifact page rules:
  - The only external scripts allowed are from cdnjs, jsdelivr or unpkg, pinned to an exact version.
  - Light and dark themes are defined through color tokens.
  - It works at phone width.
  - The only downloads from inside the page are the Export button's (`exportui.ts`): best-effort, because an Artifact frame may block them, so each falls back to showing the image to save or copy by hand.
- Comments are sparse and explain *why*.

## Working an issue
- Every PR passes `npm test` and `npm run typecheck`, and adds tests for new analysis or model behavior. The gallery-default CI job runs `npm run gallery -- --check` against `gallery/thresholds.json`; a change that makes default groupings worse fails it (`gallery/README.md`, "Default-grouping gate").
- Never commit `plugin/dist/`. The `no-dist` CI job fails any PR that touches it, because the bundle would conflict across parallel branches. After a release to `main`, `.github/workflows/rebuild-dist.yml` rebuilds the bundle and a bot commits it. If you ran `npm run build` locally, run `git checkout plugin/dist` before committing. The `Verify bundle` workflow rebuilds it on ubuntu-latest after each bot commit (and daily) and fails if it differs from the committed file; the stamp comes from the bundle's `// repoladder-build:` line. A bundle built locally (macOS) will not match, so never compare locally.
- Any PR that changes what a diagram looks like includes before/after screenshots (see below), and you look at them yourself before opening the PR.

## Branches and releases
- Feature PRs target `develop` (branch from it) and run CI when non-draft (tests, typecheck, build, gallery gate, plugin install; Windows only for install/packaging changes). Draft PRs get none.
- `develop` -> `main` is the release PR: open it ready for review (not draft), merge it with a merge commit (never squash), and it runs everything (tests, typecheck, build, gallery gate, plugin install on Linux and Windows, `no-dist`, `leak guard`). `scripts/cichanges.ts` runs everything for any PR into `main`.
- A push to `main` runs CI. A bot rebuilds `plugin/dist` on `main` and `Verify bundle` checks it; back-merge `main` into `develop` after each release as a direct push, not a PR (a PR would carry the bot's `plugin/dist` commit and fail `no-dist`).
- Leak guard: `scripts/leakguard.ts` fails on internal terms, home-directory paths and secret shapes (rules in `scripts/leakguard.config.json`, patterns only) and runs gitleaks when installed (`.gitleaks.toml`). `npm run leakguard` scans the tree (known hits in kept files are a ratchet in `scripts/leakguard.private.json`); `-- --strict` ignores that file and is the gate for a scrubbed tree; `-- --text < draft.md` or `-- --file <path>` checks a draft. Output is `file:line: [rule] why`, never the matched text. `npm run hooks` (also `prepare`) sets `core.hooksPath` to `.githooks/`, whose pre-push hook scans the lines you push (lines already on `origin/develop` or `origin/main`, e.g. from merging develop into your branch, are not rescanned; `git push --no-verify` skips it). Owner-only terms go in the gitignored `.leakguard.local.json` (`{ "terms": [...] }`). The `leak guard` CI job runs on every non-draft PR and every push to `main`, docs-only or not, and in `rebuild-dist.yml` before the bot pushes.
- The marketplace and the README install from `main` (the default branch). Required-check rules belong to the public-cut repo settings (#419); until then green CI is checked by whoever merges.

## Screenshots
`npm run shots [-- --repo name,name]` opens every gallery `diagram.html` in Playwright Chromium, visits each board through the viewer's `window.__repoladder.show(id)` hook, and saves `.gallery/shots/<repo>/<board>-<mode>.png` in three modes: `desktop-light` and `desktop-dark` (1280×800) and `phone-light` (390×844). `.gallery/shots/index.html` is the contact sheet. It needs a built gallery and takes a few seconds.

PR workflow for a visible change:
```bash
# "before": shots of the base branch, taken before you start (or from a clean checkout of it)
npm run gallery && npm run shots && rm -rf .gallery/shots-before && mv .gallery/shots .gallery/shots-before
# ...make the change...
npm run gallery && npm run shots -- --compare .gallery/shots-before
```
If you already have changes, take the "before" shots in a separate worktree of the base branch and pass `--compare <that worktree>/.gallery/shots`.
`--compare` writes `.gallery/shots/compare.html` (only the boards whose pixels changed, plus added and removed ones) and one side-by-side PNG per changed board and mode in `.gallery/shots/compare/<repo>/`. Attach those PNGs to the PR and list them under "How verified". If nothing differs, say so.

Playwright is pinned to an exact version so it uses the Chromium already in `~/Library/Caches/ms-playwright`; on a fresh machine run `npx playwright install chromium` once.

`npm run design [-- --compare <earlier .gallery/design dir>]` does the same for the viewer's panel states (selection, tour step, search, phone sheet) on offline sample maps, plus a reference of the theme tokens and controls (`src/viewer/DESIGN.md`, "Design check").

`npm run shots:phone` is the Mobile Safari check (the `phone` test tier). It serves the built demos (`npm run gallery -- --demos`) to the `repoladder Phone iPhone 15` / `iPhone SE` iOS 17.5 simulators and saves `.gallery/demos/phone/<device>/<demo>-<scheme>.png`.

## Layout lint
`src/build/lint.ts` measures every laid-out board on what the viewer draws (`outline.ts` takes the shapes from `viewer/shapes.ts` and `viewer/figures.ts`: actor cards, stacked cards, cylinder lids; labels are placed by `viewer/placement.ts`, the same call `draw.ts` makes). `npm run gallery` prints it per repo and shows it in the index table; `npm run lint:layout -- .gallery/out/<repo> [--all] [--top N]` prints the worst boards and writes `lint.json` next to the build. Run it before and after any change to layout, sizes, shapes or labels, and put the numbers in the PR.

Hard defects, which should be zero (`test/lint.test.ts` asserts it on the fixture builds; known failures are `todo` with the issue that fixes them):
- `overlap`: two boxes' drawn shapes overlap.
- `endpoint`: a wire's start is more than 2px outside its box, or its arrowhead is more than 2px off its target's drawn border (short of it, or hidden inside it, e.g. under stacked cards).
- `label`: a visible edge label covers a box or another label.
- `through`: a wire crosses a box that is not one of its ends.
- `clipped`: a visible edge label reaches past the board's fitted frame (`viewer/bounds.ts`, which pads boxes, wires and shown labels), so the fitted view would cut it off.

Coverage (`src/model/coverage.ts`): `lint.json` also holds `coverage` (`total`, `drawn`, `undrawn[]`, `noBoard`, `usesChecked`, `tourSteps`). A connection (an import or call between files, or a file's use of a service or store) is **drawn** when some board has a `major` edge between the two boxes holding its ends (`drawn.ts`'s definition). `build` prints `CONNECTIONS 1,595 connections, 0 undrawn`, then `UNDRAWN <a> -> <b>` lines (20 at most, then `+N more`) and `UNDRAWN_TOUR_STEP <tour>/<step> -> <board>` for a Default-stop tour step on a board that does not draw its edge. Those are warnings: `build` still ends in `BUILD_OK`. `npm run lint:layout`, the gallery run (it exits 1) and `npm run gallery -- --check` (model-only, first-pass model) fail on any.

Neatness, reported per board: `aligned`/`layered` (boxes in a shared layer, a column on right-flowing boards and a row on down-flowing ones, that share a left/center/right or top/middle/bottom line within 2px with another box there), `widthCV` (coefficient of variation of widths per kind), `crossings`, `overlapWires` (pairs of arrows drawn on top of each other along a shared stretch; `separateWires` in outline.ts moves them onto parallel tracks on every layout path, and `pickLayout` prefers candidates with fewer), `bendsPerEdge`/`maxBends`, `namePx` (rendered box-name size at the 1280×800 desktop fit; aim for 11.5 or more), `wasted` (share of the fitted canvas covered by no box or label) and `hiddenLabels` (labels with no free spot, shown only when zoomed in).

### Layout stability
`src/build/stability.ts` scores how much of a board's arrangement survives a change: the share of box pairs that keep their left/right/above/below relation between two layouts. Boxes are joined by id and only shared ids count; relations compare box centers on each axis, within 2px counting as the same band, and a pair is kept only when both axes match. All pairs are scored up to 400 shared boxes, above that a deterministic stride sample. `npm run stability -- <out dir | fixture:name> [...] [--before <src> --after <src>] [--board <id>]` prints the window-shape table (aspects 0.46, 1, 1.6, 2.2 and a pair either side of `LANE_TALL`), the per-board commit table (with `--before`/`--after`) and the Overview vs root shared-box score. Report-only: no threshold, exit 0. Layout-stability changes (#463, #464) are judged against these numbers.

## Digestibility budget
`src/build/budget.ts` says whether a laid-out board can be taken in at once or wants another level: over `BUDGET` (12 drawn boxes, 20 arrows, names 11.5px at the desktop fit, no files hidden in "+N more") it is over budget (a file board draws every connection, so a dense one is over budget until split; for a grouping Claude wrote, `build` also prints `WARN <leaf>: …` lines), with the reasons and the board's kind (`group`, `files`, `story`, `store`). `build` prints one `OVER_BUDGET <board> (<kind>): <reasons>` line per such board before `BUILD_OK` (not an error) and writes `lint.json` (the lint plus `budget.over` and `budget.byBoard`); `npm run gallery` shows the count per repo.
